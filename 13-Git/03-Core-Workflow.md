# Core Git Workflow & Code Review

## 1. Intro: The Git Workflow
The daily routine of a DevOps engineer involves working with Git to propose changes, review code, and integrate updates securely.

## 2. Core Concepts: The Full Git Workflow End-to-End
Here is a typical workflow for adding a new Azure Virtual Network using Terraform:

1. **Get the latest code:**
   ```bash
   git checkout main
   git pull origin main
   ```
2. **Create a feature branch:**
   ```bash
   git checkout -b feature/add-vnet
   ```
3. **Make changes:** Create `vnet.tf` and write your Terraform code.
4. **Stage and Commit:** Use Conventional Commits (e.g., `feat:`, `fix:`, `docs:`).
   ```bash
   git add vnet.tf
   git commit -m "feat: add azure virtual network module"
   ```
5. **Push to remote:**
   ```bash
   git push origin feature/add-vnet
   ```
6. **Open a Pull Request (PR):** Navigate to GitHub/Azure Repos and create a PR to merge `feature/add-vnet` into `main`. Fill out the PR template.
7. **Code Review:** Teammates review the code, leave comments, and approve.
8. **Merge:** Use a **Squash Merge** to combine all feature branch commits into a single, clean commit on `main`.

## 3. Pull Request Best Practices
- **Keep PRs Small:** Easier to review and less likely to introduce bugs.
- **Descriptive Title & Description:** Clearly explain *what* the change does and *why*.
- **Link to Ticket:** Reference the Jira/Azure Boards work item (e.g., `Fixes DEV-123`).

## 4. Code Review Checklist for Terraform/DevOps PRs
When reviewing DevOps code, check for:
- **Security:** No hardcoded secrets. Network Security Group (NSG) rules are properly restricted (no open port 22/3389 to the internet).
- **Naming Conventions:** Resources follow standard naming guidelines (e.g., `vnet-prod-eastus-01`).
- **Tags:** Required resource tags (Environment, Owner, CostCenter) are present.
- **No Hardcoded Values:** Parameters should be passed as variables.
- **CI Output:** Ensure the `terraform plan` output generated by the pipeline looks correct and doesn't destroy unexpected resources.

## 5. Git Branching Strategies
- **Feature Branch Workflow:** Every new feature/fix gets its own branch off `main`. Simple and widely used.
- **Trunk-based Development:** Developers commit small, frequent changes directly to a shared trunk (`main`) or very short-lived branches. Used in mature CI/CD environments.
- **GitFlow:** A strict model using `main`, `develop`, `feature`, `release`, and `hotfix` branches. Often too complex for continuous delivery in DevOps.

## 6. Handling Merge Conflicts in Terraform
A merge conflict happens when two people change the same lines in a file.
In Terraform, conflicts in `.tf` files are resolved manually by choosing which code to keep.
*Note: State file (`.tfstate`) conflicts should never happen because state files should be stored in a remote backend (like Azure Storage) with state locking enabled, not in Git.*

## 7. Useful Git Commands Reference Table
| Command | Description |
| :--- | :--- |
| `git log` | Shows the commit history. |
| `git diff` | Shows changes between commits, branches, or working directory. |
| `git stash` | Temporarily shelves changes you've made so you can work on something else. |
| `git stash pop` | Applies the stashed changes back to your working directory. |
| `git reset --hard HEAD` | Discards all local changes and resets to the last commit. |
| `git rebase main` | Reapplies your branch's commits on top of the latest `main` branch. |

## 8. CI/CD Integration: GitHub Actions / Azure DevOps Triggers
When a PR is opened, the hosting platform triggers a pipeline.
For Terraform, this PR pipeline typically runs `terraform plan`. The reviewer checks this plan output directly in the PR comments to verify exactly what infrastructure will be created, modified, or destroyed before approving the merge.

## 9. Interview Q&A
**Q: What is the difference between a merge commit and a squash merge?**
A: A merge commit preserves all individual commits from the feature branch and creates a new commit tying the branches together. A squash merge compresses all commits from the feature branch into a single new commit on the target branch, keeping the history clean.

**Q: Explain what `git rebase` does.**
A: `git rebase` moves the base of your branch to a new commit. It takes your commits and "replays" them on top of the target branch (like `main`), creating a linear history without merge commits.
