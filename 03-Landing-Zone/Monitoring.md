# 📊 Monitoring in the Landing Zone

> "If a server crashes in the cloud and nobody is monitoring it, did it really crash? Yes, and it probably took down the company website."

---

## 📖 Before You Read
Before you dive into Monitoring, make sure you understand:
- What **Azure Monitor and Log Analytics** are — see [[Monitor]] and [[Log-Analytics]]
- The concept of **Centralized Management** — see [[Management]]

---

## 🤔 What is it?

In an Azure Landing Zone, **Monitoring** is the automated system designed to collect, analyze, and act upon data generated by every single resource in your cloud environment.

It ensures that the IT operations team has a "single pane of glass" to view the health, performance, and security of the entire company, rather than having to log into 500 different servers to check their individual logs.

> 🩺 **Real-World Analogy:**
> Imagine a hospital patient in the Intensive Care Unit. 
> The doctors don't walk into the room every 5 minutes to manually check the patient's pulse. They hook the patient up to an ECG machine (**Azure Monitor**). 
> The machine constantly records the heartbeat to a central screen (**Log Analytics Workspace**). If the heart stops, the machine automatically blares a loud siren to wake up the doctor (**Azure Alerts**).

---

## 🧠 Why do we need it?

A cloud environment without monitoring is like flying an airplane completely blindfolded.

1. **Proactive Troubleshooting:** You want to know that a database hard drive is 99% full *before* it crashes at 3:00 AM on a Sunday.
2. **Security Auditing:** If a hacker deletes a critical production server, how do you prove who did it? Without central logs, the hacker leaves no trace. With monitoring, their IP address and account name are permanently recorded.
3. **Cost Optimization:** Monitoring tells you if a $5,000/month server has been sitting at 1% CPU utilization for six months, allowing you to downsize it and save money.

---

## ⚙️ How does it work? (The Centralized Architecture)

In a Landing Zone, you do not build monitoring on a per-app basis. You build it at the foundational level.

1. **The Central Workspace:** You create a massive, centralized `Log Analytics Workspace` inside your core Management Subscription.
2. **The Agents:** You use Azure Policy to automatically install the `Azure Monitor Agent` onto every new Virtual Machine deployed anywhere in the company.
3. **The Data Flow:** The agents stream metrics (CPU, RAM) and logs (Windows Event Logs, Linux Syslog) directly into the central workspace.
4. **The Alerts:** You write queries in the Kusto Query Language (KQL). You configure an Alert Rule: *"If this KQL query returns a CPU over 95% for more than 5 minutes, trigger a webhook to page the on-call engineer."*

## 💡 Real Example (The Application Insights Integration)

Monitoring isn't just for Virtual Machines; it's for the application code itself!

A team deploys a modern Python Web App. They hook the code into **Azure Application Insights** (a feature of Azure Monitor). 
Because the Landing Zone is configured centrally, the App Insights data flows into the same central Log Analytics Workspace.

Now, if a customer complains that the website is slow, the DevOps engineer can run a single query that traces the exact flow: *"The user clicked the button at 1:00 PM, the Python code took 5 seconds to run, and the backend SQL database took 12 seconds to respond."* The engineer instantly knows the database is the bottleneck!

---

## ⚠️ Common Mistakes Beginners Make

1. **The Siloed Workspace Anti-Pattern:** Allowing every single application team to create their own Log Analytics Workspace. This creates "data silos." You cannot easily run a single query to see if a global attack is happening across all applications at once.
2. **Logging Everything (and paying for it):** Log Analytics charges you by the *Gigabyte of data ingested*. If you tell your firewalls to log every single accepted packet, you will generate Terabytes of useless data and receive an astronomical Azure bill. Only log what provides actionable value or is required for legal compliance!

---

## 🎯 Key Takeaway
Monitoring in a Landing Zone must be centralized. By forcing all logs and metrics into a single Log Analytics Workspace using Azure Policy, you gain total visibility over the health and security of your cloud environment.

## ❓ Beginner FAQ

**Q1: What is KQL?**
> Kusto Query Language (KQL) is the language you use to search through the logs in your Log Analytics Workspace. It looks and feels very similar to SQL, but is optimized for searching massive amounts of text data extremely fast.

**Q2: How long does Azure keep the logs?**
> By default, usually 30 days. However, you can configure the Log Analytics Workspace to retain logs for up to **730 days (2 years)** if your company has strict legal compliance requirements. After that, you can archive them cheaply in an Azure Storage Account.
